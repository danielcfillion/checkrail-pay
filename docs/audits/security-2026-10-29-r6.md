# Checkrail Pay security review, round 6 (verification pass)

Reviewer: the same AI security analyst as round 5. No human security audit has been done.
Code under test: commit 43b40a6 (head of pull request 1), compared with acc039d, the code I attacked in round 5.

## 1. Executive summary

- I re-ran every round 5 reproduction against a fresh production build of 43b40a6 (fresh seed, `next start` on port 3116, mock rails, the same five logins, demo personas on). I also reviewed the 29-file diff, read the contract diff in full, ran `cargo test --locked` with the target directory under my scratch folder (16 pass), and ran the unit suite (56 files, 439 passed, 1 skipped). The server was stopped by its recorded pid, and `git status` is clean in the new checkout.
- Most of the fixes hold. The clerk can no longer plant a statement reference (SEC3-1 and SEC3-2 closed), the payout hash no longer lets a database reader recover an account number (SEC5-2 closed, and an old database fails safe), the contract's spend list is now bounded and its cap is never looser than a true rolling day (SEC2-9 closed), the PDF worker gets a bare environment (SEC5-8 closed), and the 12-character rule for live money works across every setting I tried.
- Two fixes only half hold. **SEC5-1 is partly fixed:** a clerk can no longer write a departure, but a clerk-made trip sheet still gets a payment to auto-execute against any departure an approver has listed, including one dated six weeks in the future (USD 190 settled with zero approvals, twice). **SEC2-8 is partly fixed:** items with warnings are now skipped, but items that need a person for a reason that is not a warning are still approved in bulk, and I watched a clerk-fabricated payment go through a run that way.
- **SEC2-7 is not fixed end to end.** The new mixed-script test works on a string, but policy only runs it on `obligation.sourceRef`, which can never hold a non-ASCII letter. A re-invoice written with an Armenian or Cherokee letter still gets no job key, no duplicate block, no PayPal-history block and no new warning.
- New findings from the diff: viewing a payment-run page now writes audit rows (SEC6-1, Medium), the rate-card residual above (SEC6-2, Medium), and two Info items. No new Critical or High.
- I am satisfied that no Must-fix item is outstanding, with one proviso: SEC6-2, SEC2-7 and SEC2-8 should be closed before real money, even though I label them Should-fix (section 9).

Ratings: overall security 8/10, hosted demo 8/10, moving real money 6/10 (section 8).

## 3. Re-tests and diff review

### 3.1 SEC5-1: departures (rates.ts, roles)

Reproduced on 43b40a6 over HTTP as `clerk`:
- `importDeparturesAction` with the HG-4D-9999 manifest: "clerk (AP clerk) cannot import departures". Same refusal for raising the real HG-4D-0927 to 40 vehicle-days and for the accountant. Database unchanged (`departures` has no HG-4D-9999 row, Phuong's quantity is 4). An approver import works.
- The round 5 chain (PDF, `ingestAction`) against the fake departure: `awaiting_approval`, reason "Only the vendor's own documents support this amount ...", 0 approvals. The original attack is closed.
- Not closed: the same chain against a departure that is already on file. A trip sheet PDF I wrote for CEB-2D-1024 (Rosa Villanueva, 2 days, USD 190) evaluated to `approved` / `auto_execute` with no reasons, and `executeAction` as `clerk` settled it, 0 approvals. The departure row says `created_by: user:lan`, so nobody had to touch it; the seed was written that way. See SEC6-2 for the future-dated variant.

Diff review: the only writers of `departures` and `departure_services` are `importDepartures` (now gated) and the seed. The test changes are consistent. The `ImportDepartures` button is hidden for roles without `verify_vendor`. No regression found. A cosmetic point: `seed.ts:197` still records the seeded departures as imported by the clerk persona.

### 3.2 SEC3-1 and SEC3-2: reconciliation (books.ts)

Reproduced (the round 5 script, retargeted): clerk uploads a file with payout lines for two settled PayPal payments, ids `PLANTA1` and `PLANTB1`. Result in the database: both `statement_ref` NULL; `reconciliations` row for `user:clerk` has `recorded = 0`. Accountant uploads the genuine line `REALB1` for payment B: matched. Accountant uploads a reversal citing `PLANTA1`: listed unmatched, payment A still `settled`.

Diff review (`books.ts:139`, `:212`): the persistence loop is skipped when `!canRecord`, and `canRefund` now equals `canRecord`, so nothing else changed for reconcilers. Every other write of `statementRef` or `reconciledAt` in `src` goes through this function (grep). A clerk still sees real matches, which is useful. Two small points. The server action's toast still says "2 matched" with no "not saved" (`actions.ts` message), and the Books page banner only shows for the most recent run, so a clerk can believe they reconciled. And a clerk's unsaved run is stored as a `reconciliations` row, so it appears in the history.

Residual, which the author accepted and I accept: an accountant who uploads a tampered file is trusted. I ran it: accountant uploads a clerk-supplied file whose payout line is planted (`statement_ref` becomes `PLANTC1`), then a clerk-supplied reversal citing it: settlement C moved to `refunded`. This now needs two uploads by a reconciler of files a clerk could have edited. Suggested hardening, unchanged from round 5: write `statement_ref` only from a `paypal_api` reconciliation, or re-read the original payout from PayPal when a refund is applied.

### 3.3 SEC5-2: keyed payout hash (dataKey.ts, orchestrator.ts)

- Fresh vendor, 10-digit account, same brute force as round 5: not recovered. The account number now joins the hash as `keyedDigest("payout-hash", "VCB:7283610456")`, HMAC-SHA256 under an HKDF sub-key of `CHECKRAIL_DATA_KEY` (`dataKey.ts:69`, `orchestrator.ts:394`). The sub-key is domain-separated by label.
- Upgrade: I seeded a database with the old code and a fixed key, then ran the new build on it. Maria (PayPal only, no account) was paid normally because her hash did not change. Linh (bank account) was approved, then Pay was refused with "Vendor payout details were edited without re-verification" and the obligation moved to `blocked`. A clerk's profile edit did not heal it. A clerk proposing the same details and an approver verifying them did: new hash stored, recheck, approve, pay, state `sent`. So it fails safe and recovery needs two people, as the response says.
- Rough edges, none a vulnerability: the error text blames an edit that never happened; `recheck` still says "now awaiting approval" while the stored hash is stale, so a user can loop between awaiting and blocked until the vendor is re-verified; and an in-flight `execution_pending` bank payment at upgrade time can no longer be reconciled in the app (`orchestrator.ts:991` compares the hash), only resolved by hand. `returnedToSameDetails` (`:545`) will not match refunded bank payments made before the upgrade. Worth a line in the upgrade note.

### 3.4 SEC2-8: run release (runs.ts)

Tested with run items taken from the demo and from my own clerk requests:
- Items carrying warnings: skipped. Result "1 paid, 2 skipped", message "Has 3 warnings a person must read first: Evidence supplied by operator ...; No reference supplied ...; Agent wants: ...". Good.
- The draft page shows the warnings (React inserts comment nodes between the text pieces, so a naive text search misses them; stripped, the sentence is there).
- Not fixed: the same run also contained my fabricated HG-4D-9999 payment (no departure on file). Its only reason for a person was "Only the vendor's own documents support this amount", a `require_approval` reason that is not a warning. The run approved and paid it with 0 warnings shown. The same applies to "first payment to this vendor", "above the auto-execute threshold" and the dual-approval reasons. The page shows only warnings, so the approver releasing the run never sees why those items needed them. Suggested fix: show each item's stored `policyReasonsJson` next to the item, and skip items whose reasons include anything other than amount-over-threshold, or require a tick per item.

New: `approvalWarnings` calls `runPolicy`, which writes (SEC6-1).

### 3.5 SEC2-7: look-alike references (ids.ts, policy.ts)

At string level the fix works. Run through `hasConfusables` / `mixesScripts`: Armenian Օ, Cherokee Ᏼ, Latin small capital ᴏ and the Devanagari zero all return true for both. Plain Vietnamese ("Hóa đơn HS-1027 Nguyễn Thị Linh", "ĐƠN-2026-14"), "Café-22", full-width forms and normal references are not flagged. One false positive: "10µm rod".

End to end it does nothing. I ingested a Maria Santos re-invoice (USD 181, so the same-amount rule does not fire) naming the already-paid `JOB-HG4D-0914` in the request text and evidence excerpt:

| Letter in the id | Result |
|---|---|
| ASCII | blocked: "Reference JOB-HG4D-0914 was already used", plus a PayPal-history block citing the real transaction id |
| Cyrillic О (folded) | blocked: "Same job as obligation ... both name JOB-HG4D-0914", plus the PayPal block |
| Armenian Օ U+0555 | `awaiting_approval`; `no_duplicate` passed "No earlier request matches this job"; `paypal_history` passed "no payment for this job in the last 31 days"; only warning is "No reference supplied; duplicate check relied on job identifiers and amount" |
| Cherokee Ᏼ U+13F4 | same as Armenian |

`sourceRef` is null in the last two because it can only hold ASCII (`isValidSourceRef`, the agent's `normalise`, the amend validator). `mixesScripts` is called only on `obligation.sourceRef` (`policy.ts:260`), so the new warning is unreachable and the outcome is the same as in round 5. The message the approver sees ("duplicate check relied on job identifiers") is also misleading, because the identifiers were exactly what was hidden. Fix: apply the mixed-script test to the texts the job keys are read from (request, evidence label and excerpt, document text, PayPal notes) in `ownJobKeys` / `jobKeys`, and raise a block-or-warn there; or make `jobKeys` treat any token that mixes ASCII with non-Latin letters as a candidate key after dropping the odd character.

### 3.6 PDF worker environment (documents.ts)

`env: { PATH, NODE_ENV: "production" }` replaces the inherited environment entirely, so the Anthropic key, PayPal secret, Stellar seed and data key are not visible to the child. pdf.js still extracted text under it (HTTP upload, browser upload and tsx upload all returned `reader: pdf-text`). Fixed.

### 3.7 Opt-in log line (middleware.ts:69)

With `CHECKRAIL_LOG_CLIENT_IP=1` a wrong password writes one `console.warn` with an object holding the throttle key and four address headers. It does not include the Authorization header or the password (checked in the server log). Values are printed through object inspection, so a hostile header cannot forge extra log lines. Off by default; `render.yaml` sets it to "0". It can bloat logs under a guessing flood while enabled, which is the intended short diagnostic window. Fine.

### 3.8 12-character rule (basicAuth.ts)

I started the production build under seven settings. Results: `PAYPAL_ENV=live` with a 5-character password: 503 with the new message; with a 12-character password: 200; `WISE_ENV=live` and `STELLAR_NETWORK=public` with 5 characters: 503; `CHECKRAIL_BASIC_AUTH=owner:short` under `PAYPAL_ENV=live`: 503; `PAYPAL_ENV=sandbox` with 5 characters: 200 (exempt by decision); `RAIL_MODE=live` with sandbox settings and 5 characters: not 503 (it then answers 500 because no Stellar secret is set, as expected). No network was contacted. Two notes. The rule is a length rule, not an entropy rule ("password1234" passes). And the new `realMoneyEnv` helper includes `WISE_ENV=live`, but `personasAllowed` (`basicAuth.ts:122`) still checks only `PAYPAL_ENV` and `STELLAR_NETWORK`, so demo personas stay switchable when only Wise is live. Personas do not defeat separation of duties (logins are counted), so this is Info (SEC6-4), but the two should share one helper.

## 4. Contract review (cargo test and source)

`cargo test --locked`: 16 passed, 0 failed (11 old plus 5 new). Re-read the diff.

- **Hourly buckets.** `record_spend` merges into the last entry when it is the current hour, otherwise pushes. `recent_spends` keeps entries with `at + DAY >= hour_start(now)`, so it holds at most 25 hourly entries (hours floor-24h to floor). Ledger time does not go backwards, so only the last entry can be the current hour. The vector cannot grow with the number of payments. Instance storage no longer fills, so the SEC2-9 freeze is closed.
- **Is the cap ever looser than a rolling 24 hours?** No. A payment made at time t in hour H stays counted until `hour_start(now) > H + DAY`, which is at least t + 24h and at most t + 25h. A true window `[now - 24h, now]` is always inside the counted span `[hour_start(now) - 24h, now]`. `release` checks `spent + amount <= daily_cap` against that span, and `propose` also counts pending, so released spend in any 24-hour window cannot exceed the cap. The price is conservatism: up to one extra hour of cooldown. I reasoned this and confirmed the author's rolling test; I did not write my own property test.
- **Other changes.** `check_limits` now includes `cancel_window >= 60`, used by constructor and `set_limits`; the constructor and `set_agent` refuse owner equal to agent; `set_agent` requires the owner's auth and keeps the old agent's pending proposals alive, which the owner must cancel (documented). Events added for payee, limits, agent, withdraw. I found no new vulnerability. Overflow checks stay on.
- **Still open (documented):** pending payments never expire and there is no bulk cancel, so a leaked agent key plus a rotation still leaves its earlier proposals to be cancelled one by one while `release` is permissionless; no storage TTL extension, so an idle contract can be archived until someone restores it. Neither moves funds. Both should be closed before the contract holds money.

## 5. SEC5-10: document upload "No file received."

Diagnosed in four tool calls. **It works in a real browser, and the failure was my harness.**
1. Chromium (Playwright) against the production build, signed in as the clerk, `/obligations/new`, `setInputFiles` on the file input: the page posted to the server action, answered `{"ok":true,"message":"Read trip9999.pdf with the text reader.","upload":{...}}`, and showed "trip9999.pdf: read by the PDF text reader".
2. I captured the browser's request body. React names the file part `_1_file` and sends it before the part named `0` (`["$K1"]`). My Python, Node and curl bodies used `1_file` and put `0` first. When `0` arrives first the decoder builds the form before the file part exists, so `form.get("file")` is empty.
3. Replaying a body in the browser's order with the browser's field name over curl returned `ok:true`. The same fix in my harness lets me upload over HTTP (used in the CEB-2D-1215 test).

So the production build is not defective and round 5's SEC5-10 should be closed. Everything I attributed to the HTTP upload in round 5 stands, since `uploadDocument` is the function the action calls.

## 6. The author's three decisions

1. **Keep a clerk sending Assist-cleared payments: accept the principle, reject the supporting claim.** The response says the clerk "cannot change what counts as support that is not the vendor's". True for the manifest and rates, but the clerk still supplies the only proof the job happened. I showed a clerk-made trip sheet paying USD 190 for a departure on 15 Dec (today 29 Oct) with 0 approvals, and a second one for a past departure. The cheap closers are an end-date condition on rate-card independence and a warning when the document was uploaded by the same login who prepared the request (`attachments.uploaded_by` is already stored). With those I would accept the decision as written. Without them it is a pay-before-delivery path for a colluding vendor, bounded by the threshold and the vendor daily cap (SEC6-2).
2. **No per-username lockout: accept for the hosted demo, not as a general position.** For a credential published to judges, guessing is not the threat and a username lockout would be a lever for denial of service. But the compensating controls are weaker than stated. The per-address throttle can be bypassed where nothing overwrites the header (in round 5, twelve consecutive wrong guesses with a rotating `X-Forwarded-For` all returned 401), and a 12-character minimum does not stop a guessable password. For live money I would add a per-username progressive delay (slow the response, never refuse a correct password) rather than a lockout.
3. **Do not set the Render client-address header blindly: accept, with a correction to the risk text.** Not guessing the header is right, and the diagnostic is the correct way to settle it. But "the worst case is that visitors share one throttle key, which can slow logins down" understates the failure. I showed in round 5 that when the key is shared and over its limit the correct password is refused with 429 for the whole window, for everyone on that key. Eleven wrong passwords from one visitor would lock every judge out for 15 minutes, repeatedly. Since the hosted credential is public and the throttle protects nothing there, the hosted demo should either raise `FAIL_LIMIT` a lot or skip the lockout when the credential presented is valid. That is a one-line change and removes the lever.

## 7. New findings

### SEC6-1: Viewing a payment run writes to the database and to the audit log (Medium, Should-fix)

Where: `src/lib/engine/runs.ts:97-98` (`approvalWarnings` calls `runPolicy`), `:111` (called for every awaiting item on each `viewRun`).

`runPolicy` is not read-only: it recomputes withholding, rewrites `policy_decision`, `policy_reasons_json`, `blocked_reason` and `updated_at`, appends a `policy.evaluated` audit row, and can supersede approvals. Every render of a run page with N awaiting items now does all of that N times. Reproduced: with two awaiting items, an accountant opening `/runs/<id>` moved the audit maximum sequence from 721 to 723 (two `policy.evaluated` rows by actor `policy`); the approver's Daily close sign-off with the sequence they had loaded was then refused with "Something changed since this page loaded", and succeeded after reloading. Any role that can read the page (accountant, clerk) can bloat the audit log by refreshing and can keep invalidating other people's sign-offs.

Fix: give policy evaluation a pure variant that returns the rules without persisting (`evaluatePolicy` is already pure; only the orchestrator wrapper writes), and use it in `approvalWarnings`. Persist only on release.

### SEC6-2: A clerk-made trip sheet still pays an approver-listed departure, including a future one (Medium, Should-fix; residual of SEC5-1)

Where: `src/lib/engine/rates.ts:145` (`expectedAmount` has no date test), `src/lib/domain/policy.ts:72-78` and `:347` (provenance "document" raises no warning; a rate-card match counts as independent), `src/lib/auth/roles.ts:40` (clerk holds ingest and pay).

Reproduced twice (section 3.1 and this): an approver imports `CEB-2D-1215` (15 Dec 2026, Rosa Villanueva, 2 days, rate USD 95); the clerk uploads a PDF saying the trip is closed, files the request and pays it. State `settled`, 0 approvals, USD 190, six weeks before the departure.

Why Medium: it needs an existing, approver-managed departure for the vendor and is bounded by the auto-execute threshold (USD 250 in Assist, 500 in Autopilot) and the per-vendor 24-hour cap (USD 1,000), and the vendor's real invoice would later be blocked as a duplicate. But it is payment before delivery on the clerk's say-so, for a colluding vendor. Fix: treat a rate-card match as independent only when the departure's `end_date` is on or before today, and raise the provenance warning when the uploader of the document is the preparer.

### SEC6-3: Persona gate ignores Wise live (Info)

`src/lib/basicAuth.ts:121-124`. The new `realMoneyEnv` (`:21-23`) includes `WISE_ENV=live`; `personasAllowed` does not. Demo personas can stay switchable with only Wise live. Personas still count as the real login for approvals, so no separation-of-duties break. Reuse `realMoneyEnv`.

### SEC6-4: Upgrade notes and small gaps (Info)

(a) After upgrade, in-flight `execution_pending` bank payments cannot be reconciled in the app (`orchestrator.ts:991`) and pre-upgrade refunds to bank vendors no longer match `returnedToSameDetails` (`:545`); say so in the upgrade note. (b) The clerk's reconcile toast does not say "not saved". (c) The `10µm` style false positive of `hasConfusables`. (d) With the 12-character rule scoped to live PayPal, public Stellar and live Wise, a deployment with `RAIL_MODE=live` on sandbox settings that stores real-looking bank numbers keeps short passwords; consistent with the stated decision, worth knowing.

## 8. Ratings

- **Overall security: 8/10 (round 5: 7).** The two Highs I could reproduce are closed, the data-key bypass is closed, the contract's storage freeze is closed, and the diff introduced no Critical or High. It is not higher because one fix is not wired to the input that matters (SEC2-7), two are partial (SEC5-1, SEC2-8), and the diff added a write on a read path (SEC6-1).
- **Hosted demo: 8/10 (unchanged).** Mock rails, enforced logins, a generated data key and a clean unit suite make it safe to hand to judges; the remaining weaknesses are the shared published credential, shared state (SEC2-5) and a throttle whose behaviour on Render is unknown, where one visitor may be able to lock everyone out (decision 3).
- **Moving real money: 6/10 (round 5: 4).** The clerk can no longer plant a reversal anchor or invent a departure, bank numbers are safe from a database leak, and the contract no longer has a freeze path, but a clerk can still pay a colluding vendor early (SEC6-2), the PayPal duplicate check still fails open (SEC5-5), "nothing moved" is still unchecked (SEC5-4), Stellar, Wise and live PayPal have never run, and no human has audited it.

## 9. Verdict on Must-fix items

I am satisfied that no Must-fix item is outstanding, using the round 5 meaning (would not let real money move): SEC5-1's original mint-support path, SEC3-1 and SEC2-9 are fixed and verified. My satisfaction carries one proviso: SEC6-2 (end-date condition), SEC2-7 (apply the mixed-script test to job-key text) and SEC2-8 (show non-warning approval reasons in a run) should be done before the first real payment, and SEC6-1 before the next review round, because they are cheap and they are the places where a verified fix did less than its description. Contract expiry and TTL stay open, to be done before that contract holds funds.
