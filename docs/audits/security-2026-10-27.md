## Checkrail Pay security audit, 27 Oct 2026 (round three)

### 1. Executive summary
- The money core is still the strongest part and still held every probe I threw at it: compare-and-swap transitions, refusal to execute while any attempt is open, same-key reconcile, the payout hash pinned at approval and re-checked inside the execution lock, and the bank-file and run paths reusing that one execute path. I found no new double-pay through the state machine, no bank-file formula injection, no ReDoS, no injection through the public pages or ?lang, and the public/internal action boundary, auth, security headers, tick CSRF and the matcher all held.
- The headline problem this round is that the round-two G1 fix does not work in the built app. The whole login-attribution layer the team added is inert at runtime: `currentLogin()` returns null for every server action and page, so no approval, vendor change, run or audit row ever records the real login. Because of that, one admin login using the demo personas can again counterfeit a second approver, satisfy separation of duties against itself, and verify its own vendor payout change, and the audit still does not show the real person. I reproduced all three over HTTP. The team's response marks G1 "Fixed"; it is not, in the production build.
- The other new finding is in PayPal reversal reconciliation. An uploaded activity CSV can mark a settled payment refunded with no check that the reversal line maps to the original payout; the match is amount plus currency plus email only, so it can hit the wrong payment, and a refund reopens the bill and clears duplicate protection, which lets the same job be paid again. A single clerk (the preparer role, which has `pay`) can do this with a hand-made CSV. I reproduced it.
- The round-two G3 fix is only partly in place: tax form, tax type, withholding rate, retainer and phone are now behind the checker, but a clerk can still change a vendor's `country` alone, which is what decides the withholding jurisdiction. I reproduced a clerk dropping 24% US backup withholding to zero by flipping a US vendor to CA.
- Everything else from round two holds: hard caps, enforced auth with roles, DoS fixed, genuine maker-checker on payout details (when personas are off), the self-attested-document auto-execute block (G4), security headers, the storage cap, the webhook body cap, the dev-key boot warning (G6), and rail-figure labelling (G7).

Checks: `npx vitest run` on the dual-control and people suites passes (5/5); the full build is clean; `npm run build` is OK. I seeded `./data/sec3.sqlite`, ran the production server on :3104 with five role logins (owner admin, appr and appr2 approvers, clerk, acct accountant) and `CHECKRAIL_DEMO_PERSONAS=1`, attacked it as each role, persona and unauthenticated, and stopped it by PID. Harness and scripts in `/tmp/claude-0/-home-claude/11b88efa-03f4-5292-ba70-6074dd94746e/scratchpad/a3/`.

### 3. Details

**H1 The login-attribution layer is inert in the production build (High for the demo's integrity; not reachable with real money)**
- What is wrong: the G1 fix routes "who is really acting" through an `AsyncLocalStorage`. The server-action layer calls `enterLogin(actor.viaLogin ?? actor.username)` in a per-request helper (`currentActor`, src/app/actions.ts:53), and the engine reads it with `currentLogin()` (requestContext.ts:15-17). In the built Next server, `enterWith` set inside that helper does not survive into the rest of the request, so `currentLogin()` returns null everywhere. `humanOf(actor, null)` then falls back to the actor's own username, which for a persona is the persona, not the owner behind it. The unit tests pass because they call `enterLogin` inline in the same synchronous flow; the gap is only in the Next runtime (React's flight server restores async-context snapshots around the action, discarding an `enterWith` done mid-request). The fix needs `AsyncLocalStorage.run(store, () => ...)` wrapping the engine call, not `enterWith`.
- Reproduced, three ways, on :3104 with personas on:
  1. Approvals and runs never record the login. After a persona-made ingest and an owner approval, `approvals.login`, `vendor_changes.requested_login` and `payment_runs.created_login` are all null in the database, and `obligation.created` / `approval.granted` / `execution.started` audit rows made through a persona carry no `login` in their detail. If the fix worked these would read `owner`.
  2. Dual control defeated. On a USD 6,000 payment (above the USD 5,000 dual threshold) I approved once as `owner`, called `setPersonaAction("daniel")`, approved again as `user:daniel`, and paid it as `daniel`. Two approvals, one human; the audit names `user:daniel` with no trace of `owner`.
  3. Separation of duties defeated and vendor maker-checker defeated. Owner acting as persona `lan` prepared an obligation, then owner (its own login) approved it, with other approvers present: allowed, because the preparer counts as `lan` and the approver as `owner`. Separately, owner proposed a payout change on a vendor and, as persona `minh`, verified its own change, moving a real vendor's PayPal address to `attacker@evil.example`, recorded as verified by `user:minh`.
- Impact: on the hosted demo the dual-control, separation-of-duties and maker-checker story is theatre again, exactly as in the original G1, and the audit cannot tell you which human did it. It is gated to mock rails (`personasAllowed` is false for live PayPal or public Stellar), so it cannot move real money, but it is the control the product is judged on. It also means that for non-persona use the audit simply never records a login, so the new `login` column is dead weight.
- Fix: wrap each request's engine work in `AsyncLocalStorage.run()` with the login, or pass the login explicitly through the call chain rather than through `enterWith`. Add an integration test that asserts `approvals.login` is set after an HTTP action, not just the in-process unit test.

**H2 Reversal reconciliation refunds a payment with no link to the original payout (High for real money)**
- What is wrong: `reconcilePayPal` treats any incoming line matching `reversal|returned|unclaimed|refund` as money coming back, and matches it to a settlement by currency, exact gross amount and (if present) recipient email only (books.ts:152-162). It never checks that the reversal references the transaction id of the payout we actually recorded. A matched settlement that is `settled` is transitioned to `refunded` (books.ts:174-179), which removes it from the bill's committed total (the bill reopens) and from the duplicate check's live set, so the same job can be requested and paid again. The action is gated to `reconcile` or `pay`, and the clerk role has `pay`, so a single preparer can run it.
- Reproduced on :3104: as `clerk` (and again as `acct`) I uploaded a hand-made CSV with one line `Reversal,Completed,USD,200.00,...,phuong.transport@example.com` and no real reversal behind it. It marked the settled payment INV-PHU-1101 (Phuong, USD 200) `refunded`. A fresh obligation for the same reference then passed the duplicate check ("Reference and job identifiers have not been paid before") where it would otherwise have been blocked. An earlier forged line for Jake at USD 450 refunded the first unused USD 450 settlement for that email, not a specific transaction, showing the match can also hit the wrong payment on a legitimate but ambiguous statement.
- Impact: with live PayPal this is a double-payment enabler: one preparer, one crafted or simply ambiguous statement, and an already-paid invoice is payable again with the duplicate guard silenced. Even honestly, two payouts of the same amount to the same email make the reconciler refund whichever it matches first.
- Fix: match a reversal to the settlement by the original payout's transaction/batch id (PayPal reversals carry the reference to the original transaction), not by amount and email; require that id to be one Checkrail Pay issued. Refuse to refund more than one settlement per reversal line. Consider making reversal-driven refunds a `reconcile`-only action with a second-person confirmation before a reopened bill can be paid again.

**M1 A clerk changes the tax jurisdiction field alone (continuation of G3)**
- What is wrong: the G3 fix put `taxType`, `taxForm`, `withholdingBps`, `retainerMinor` and `phone` behind `verify_vendor` (vendors.ts:187-190), but `country` is still an ordinary profile field a clerk may change with `edit_vendor`. `country` is exactly what `withholdingFor` keys on (taxes.ts:39,42,49): US backup withholding applies only while the vendor's country is US.
- Reproduced on :3104: I created a US creator with no W-9 (24% backup withholding applied: USD 48 withheld on a USD 200 payment), then as `clerk` changed the vendor's country to CA and rechecked. The withheld amount dropped from USD 48 to nothing, with no second person. Country also moves the payment onto a different corridor and silences the W-9 requirement.
- Impact: a single preparer can stop tax being withheld by moving a vendor's country, the same compliance and money exposure G3 was meant to close. The G3 name-uniqueness re-check on edit does hold (I confirmed a rename onto another vendor's exact name is refused), so that half is fixed.
- Fix: put `country` behind `verify_vendor` as well, or re-run withholding and warn when a country change would change tax treatment.

**M2 The default team still deadlocks above the dual-approval threshold (G2)**
- What is wrong: the G2 fix added `dualControlGap`, which warns on Settings and on a waiting payment when fewer than two people can approve the amount (surfaced at settings/page.tsx:38 and obligations/[id]/page.tsx:47). It does not change the control: new approver logins still default to a USD 1,000 limit and only an admin has a higher one, so a team of one owner-admin plus capped approvers still cannot get two qualifying approvals on a payment above USD 5,000.
- Reproduced: on the USD 6,000 payment, `appr` and `appr2` (USD 1,000 limit) are both over limit, `owner` can approve only once, and the only way it moved was the persona trick in H1. The warning tells the operator to raise a second limit, which is the right nudge, but the pressure to weaken a control to pay a large invoice remains.
- Fix: as before, make it easy to grant a second high limit; the warning is a good addition but not a fix on its own.

**L1 Vendor evidence can supersede the business's own records (design)**
- What is wrong: `addEvidence` (orchestrator.ts:1074-1088), used by the vendor evidence link, supersedes earlier evidence of the same kind when the vendor uploads an `invoice` or `receipt`, with no provenance filter, so a vendor upload can supersede the business's own invoice-kind row. `processObligation` then re-reads, and a vendor's figure can move the obligation amount if a person had not amended it. In practice the independent kinds that clear auto-execute (`job_sheet`, `booking`, `purchase_order`) are not superseded, and any vendor-provenance evidence raises R3b, which forces a human approval, so a vendor cannot silently raise what is paid. Still, letting a payee's upload replace the business's own record of the same kind is the wrong default.
- Fix: never supersede a `system`-provenance record with a `vendor` one; keep both and show the difference to the approver.

**L2 Amend still accepts `vendorId` (G10, unchanged)**
- `validateAmendPatch` still allows `vendorId`, and `amendObligation` refuses to change the payee only when the obligation already has one (orchestrator.ts:654-655). I confirmed the refusal on a vended obligation. The residual exposure is only an obligation with no matched payee, where a clerk amend can set any vendor and a fresh approval is then required. Drop `vendorId` from amend or require a second person when it is used.

**L3 Period lock local-day bucketing (G8, accepted)**
- Reproduced: with the books closed through the prior day, amending an obligation whose timestamp falls in the late-UTC part of that day was allowed, because in the business's +07:00 day it belongs to the next date. The team has accepted this as local-day accounting; it remains a latent off-by-one at the boundary.

**L4 Multi-tenant scoping (G5 mostly closed)**
- Obligation actions now go through `assertOwnObligation` (orchestrator.ts:1035-1037, wired at actions.ts:61), so the latent IDOR G5 named is closed for obligations, and the new run, bank-file, bill, rate and reconciliation actions scope by `businessId`. One query still does not: the bank-file "who downloaded it" maker-checker lookup selects `bank_file.downloaded` audit rows across all businesses before filtering by `batchId` (bankFiles.ts:94-100). Single-business today, so Info; scope it by business before multi-tenant.

**I1 CSP allows inline script**
- The response CSP is `script-src 'self' 'unsafe-inline'`. I found no reflected or stored sink (no `dangerouslySetInnerHTML`, React escapes output, the ?lang and public pages are safe), so this is defence-in-depth only. Tighten with a nonce if inline scripts can be removed.

### 4. Status of the round-two findings (G1 to G10)

- G1 (personas defeat dual control, audit hides the real login): **Reopened.** The fix is present in source but does not take effect in the built server; `currentLogin()` is null at runtime, so personas again counterfeit a second approver, defeat separation of duties and verify their own vendor changes, and the audit does not record the acting login. See H1. Reproduced over HTTP.
- G2 (default team deadlocks above the dual amount): **Partly addressed.** A warning now surfaces (`dualControlGap`), but the control is unchanged and the deadlock still happens. See M2. Reproduced.
- G3 (clerk changes tax fields and renames vendors): **Partly fixed.** Tax type, tax form, withholding rate, retainer and phone are now behind `verify_vendor`, and the name-uniqueness check is re-applied on edit (both confirmed). But `country`, which decides the withholding jurisdiction, is still clerk-editable. See M1. Reproduced.
- G4 (self-attested documents auto-pay in assist mode): **Fixed.** A document-provenance invoice with no independent support (no job sheet, booking, purchase order or rate-card match) now requires a person in every mode. Reproduced: a self-made Rosa PDF for USD 120 went to `awaiting_approval` with the reason "Only the vendor's own documents support this amount". A document backed by a rate-card departure still auto-executes, which is the intended behaviour.
- G5 (obligation actions not business-scoped): **Fixed for obligations** via `assertOwnObligation`; one bank-file audit query remains unscoped (L4). Read.
- G6 (dev data key derivable from source): **Mitigated.** The loud boot warning fires ("CHECKRAIL_DATA_KEY is not set: bank account numbers are encrypted with the public development key"). Reproduced on seed. Live rails still refuse without a real key.
- G7 (Wise untested, local figures modelled): **Fixed (labelling).** `settleFromRail` now records a note saying where each figure came from (simulated, Wise beta quoted, modelled bank charge). Read.
- G8 (period lock day bucketing): **Accepted, unchanged.** See L3. Reproduced.
- G9 (postcss advisory inside next): **Accepted.** Build-time only. Read.
- G10 (amend accepts `vendorId`): **Unchanged, by design.** See L2. Reproduced.

Round-one fixes spot-checked and still holding: auth enforced (401 without credentials), security headers present (CSP, X-Frame-Options: DENY, frame-ancestors none, HSTS, nosniff, Referrer-Policy, Permissions-Policy, no X-Powered-By), the matcher no longer leaks (/favicon.icox is 401), the amount and date extractors are linear (tested to 40k-80k chars, all sub-10 ms), the tick endpoint needs auth plus a token or the custom header, and bank-file content fields are neutralised by `bankText` and `csvCell` together (= + @ stripped, CR/LF quoted). The public/internal action boundary holds: internal actions posted to a public path return "Not signed in" and the onboarding action posted to an internal page is refused.

### 5. Ratings

- Overall security: 6/10. Down from 7. The money engine is still strong and most round-one and round-two holes stay closed, but the control the product leads with, dual control with a truthful audit, does not actually hold in the running app (H1), and a single preparer can reopen an already-paid invoice through reversal reconciliation (H2). Those two pull it back below where round two scored it.
- Fit to run the hosted hackathon demo: 7/10. Down from 8. Auth, roles, caps, mock rails and the DoS fixes still demo well and no real money is at risk, but the headline dual-control demo is not genuinely enforced (one judge logged in as owner can approve twice and pay, and the audit will not show it), so the story shown to judges overstates the control. Turning personas off removes the shortcut but then the demo cannot show two approvers at all.
- Fit to move real money for a small business today: 3/10. Down from 4. New blockers on top of the round-two list: reversal reconciliation lets one clerk refund a payment with no link to the original payout and re-pay the job (H2), a clerk can move a vendor's tax jurisdiction alone (M1), and the audit log does not record who really acted when personas are used. Fix the login wiring so dual control and the audit are real, bind reversals to the original transaction, gate `country` behind the checker, and resolve the dual-approval deadlock before real money.
