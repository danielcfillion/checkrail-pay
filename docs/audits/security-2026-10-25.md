## Checkrail Pay security audit, 25 Oct 2026

### 1. Executive summary
- The money-path internals are careful. Transitions use compare-and-swap, execution runs in a transaction, idempotency keys are reused correctly, failed and unknown outcomes are kept apart, the payout hash is pinned and policy is re-run at execution. I found no double-pay or state-machine bypass.
- The weak points sit around that core. There is one shared identity, so there are no roles and no real dual control. Autopilot caps set to "0" mean "no cap". Auth is off unless an environment variable is set. The Render blueprint wipes the database on every boot.
- Any authenticated user (and, in a real deployment, any supplier whose document gets uploaded) can freeze the whole single-process server for minutes with one crafted text file or PDF. I proved this over HTTP.
- I found no auth bypass, no actor spoofing, no server-action CSRF, no XSS and no SQL injection. I tried path tricks, the image optimizer, `x-middleware-subrequest` and forged headers.
- Dependencies: Next 15.5.27 has a server-action DoS advisory and should go to 15.5.28. The critical image-optimizer advisory is mitigated, because the lockfile pins sharp 0.35.5.

Checks: `npx vitest run` passes 213/213, `npx tsc --noEmit` is clean and `npm run build` is OK. The server was attacked at :3101 with `CHECKRAIL_BASIC_AUTH=judge:test123` and has been stopped. My harness is in `/tmp/claude-0/-home-claude/11b88efa-03f4-5292-ba70-6074dd94746e/scratchpad/sec/` (`act.py` calls server actions by ID).

### 3. Details

**F1 Event-loop DoS (Medium, CVSS about 6.5, AV:N/AC:L/PR:L/A:H)**
- **What's wrong:** In `extractAmount`, the pattern `(\d{1,3}(?:,\d{3})+|\d+)...(USD|...)` can restart after every comma, because the lookbehind does not exclude `,`. The cost grows with the square of the input.
- **Measured:**
  - `000,000,...`: 64 KB took 0.76 s, so 640 KB is about 76 s.
  - Over HTTP, uploading a 240 KB `.txt` made `GET /` from another client wait 9.8 s.
  - `pdfText` runs pdf.js on the main thread with no limit on decompressed size. A 583 KB FlateDecode PDF (300 MB inflated) froze the server for 53 s, and RSS rose to about 370 MB. Render free has 512 MB, so a larger file will likely OOM it.
- **Impact:** On the hosted demo any judge can stall everyone, including the autopilot heartbeat. In a real deployment the input is supplier-controlled: one invoice PDF or email body takes the app down.
- **Fix:**
  - Rewrite the amount regex so it is anchored and linear (add `,` to the lookbehind set, bound `\d+` to `\d{1,12}`), or scan tokens instead.
  - Cap the text passed to the extractors (for example the first 20 KB).
  - Run pdf.js in a `worker_thread` with a timeout and memory limit, and abort when total extracted text passes a cap.
  - Cap the request body for text uploads.

**F2 "0" caps are unlimited (Medium)**
- **What's wrong:** Policy only applies the per-payment and daily autopilot caps when they are `> 0`. `setAutonomy` accepts 0, and the UI says "zero or more". A user who types 0 to mean "nothing" gets "no limit".
- **Reproduced:** I set caps to 0/0 with a 0 s window, then uploaded three self-made PDF invoices of $990 each. All three settled as `agent:autopilot` with 0 human approvals: $2,970, against defaults of $500 per payment and $2,000 per day. Only the $1,000 per-vendor cap and the $5,000 dual-approval threshold remained.
- **Fix:** Require caps of at least 1. Represent "no cap" explicitly and never offer it for autopilot. Set a minimum cancel window (for example 60 s). Ask for confirmation when caps are raised.

**F3 Fail-open auth (Medium; High with live rails)**
- **What's wrong:** If `CHECKRAIL_BASIC_AUTH` is unset, every page and action is open and the actor is the hardcoded `user:daniel`. render.yaml marks the variable `sync: false`, so a forgotten dashboard entry publishes the app openly. Nothing stops `RAIL_MODE=live` without auth; only a comment in `.env.example` warns against it.
- **Fix:** Refuse to start (or return 503) when `NODE_ENV=production` or `RAIL_MODE=live` and no credential is set. Allow open mode only through an explicit `CHECKRAIL_INSECURE_DEMO=1`.

**F4 Boot-time wipe (Medium for any real use of the blueprint)**
- **What's wrong:** `startCommand: npm run db:seed && ...`, and `seedDemo` calls `resetDemo`, which deletes audit_entries, payment_attempts, settlements and every other table. Only `resetDemoAction` checks `isLiveRails()`. The CLI seed has no check.
- **Impact:** The blueprint's own comments invite flipping `RAIL_MODE=live`, and Render free spins down on idle. Every wake-up would then erase:
  - payment history, which is what duplicate detection reads, so an already-paid invoice is no longer flagged;
  - unknown-outcome attempts and their idempotency keys;
  - the audit trail.

  It also re-creates an "approved (PayPal)" obligation ready to send.
- **Fix:** In seed.ts, refuse when `isLiveRails()` or when the DB already holds non-demo data. Seed only when the DB is empty, or put the reset behind a separate demo-only start command.

**F5 Identity model (Medium)**
- **What's wrong:** One credential gives one actor. Distinct-approver counting therefore tops out at 1.
- **Reproduced:** A $6,000 invoice was approved once and stayed "1 more approval needed". A second try returned "already approved". Payments over $5,000 can never be made.
- **Live mode:** `requireSeparateApprover ?? isLiveRails()` means that, with one credential, nothing ingested through the UI can be approved at all.
- **No roles:** Anyone holding the credential can change autonomy and caps, reset, approve and execute. The credential goes in the Devpost instructions.
- **Fix:** Use per-user credentials or SSO. Put roles (admin for autonomy and caps, approver, preparer) on the server actions. Keep dual control and separation of duties keyed on real identities.

**F6 Self-attested evidence clears autopilot (Medium, design)**
- **What's wrong:** A PDF whose proposed row is left untouched gets provenance "document" and raises no warning. The invoice is the payee's own claim, yet it names the vendor and matches the amount, so policy reaches auto_execute.
- **Reproduced:** A PDF I wrote myself for Rosa ($120) was scheduled and sent by autopilot with no person involved.
- **Impact:** The PDF check only shows the operator didn't type the figures. It proves nothing about the job. In a real deployment a supplier inflating or inventing an invoice under a fresh reference is paid automatically up to the caps.
- **Fix:** Before autopilot may act, require an independent record from a different source (job sheet, booking or PO from a system integration, or a prior contract rate), or give each vendor an expected-amount band. Treat payee-authored documents as "claim", not "proof".

**F7 CSV CR injection (Low)**
- **What's wrong:** `esc()` quotes only `"`, `,` and `\n`, and checks formula prefixes only at the start of a field.
- **Reproduced:** The request text `Kalaw Trekking Collective USD 420 JOB-KAL2D-1079\r=cmd|' /C calc'!A0` produced an unquoted field holding a bare CR. Importers that treat CR as a line break start a new row beginning with `=cmd|...`. The file comes from `GET /api/accounting/export`.
- **Fix:** Quote any field containing `\r`, or strip control characters. Neutralise formula characters after any line break as well.

**F8 Stale release time (Low)**
- **What's wrong:** Manual `executeAction` on a scheduled payment does not clear `releaseAt`. After a rail failure and `retryFailedAction`, the obligation is approved again with the old `releaseAt`.
- **Reproduced:** Autopilot logged `autopilot.releasing` on the next heartbeat with no new window. The same happens for execute-refused (blocked) payments that are later amended. This contradicts the comment at autopilot.ts:102.
- **Fix:** Clear `releaseAt` inside the execution-start transaction and in `retryFailed` and `amendObligation`. Reschedule explicitly.

**F9 Ingest robustness (Low)**
- **What's wrong:**
  - An evidence row with `label: null` failed after the obligation row was inserted, leaving an orphan `drafted` obligation. Any attachment already linked becomes unusable ("already attached").
  - `sourceType` is stored unchecked (I stored `<img src=x onerror=alert(1)>`; React escaped it).
  - Evidence `amountMinor` accepts floats and negatives (stored as REAL 18000.4, which produced a "differs by USD 0.00" warning).
  - Evidence count and length are unbounded.
- **Fix:** Wrap ingest in one transaction. Validate with zod: enum sourceType, safe-integer amounts, ISO currency, length and count limits.

**F10 Headers (Low)**
- **What's wrong:** Pages carry no CSP, `frame-ancestors` or `X-Frame-Options` (clickjacking), HSTS, `nosniff` or Referrer-Policy.
- **Fix:** Add them via `headers()` in next.config, and set `poweredByHeader: false`.

**F11 Matcher prefixes (Low)**
- **What's wrong:** `(?!...|_next/image|favicon.ico)` also matches `/favicon.icox` and `/_next/imageX`. These return the app's 404 page without auth, and that page shows "Ridgeline Expeditions LLC" and "PayPal mock / Stellar mock / Agent rule-based / Books csv".
- **Server actions to those paths:** Not executed (tested).
- **Fix:** Anchor the exclusions (`favicon\.ico$`, `_next/image$`, `_next/static/`). Don't render business data in the root layout for unauthenticated 404s.

**F12 Webhook (Low, live only)**
- **What's wrong:** `await req.text()` has no size limit, and every unauthenticated request triggers an OAuth token check and a verify-webhook-signature call to PayPal.
- **Fix:** Reject bodies over about 64 KB and require the PayPal headers before reading. Rate-limit by IP.

**F13 Audit growth (Low)**
- **What's wrong:** `confirmSettlement` writes `settlement.checked:*` on every poll. An UNCLAIMED payout (up to 30 days) produces about 5,760 rows a day, and the obligation page loads all of them.
- **Fix:** Audit only on status change and back the polling off.

**F14 Dependencies**
- `next@15.5.27`:
  - GHSA-p3m5-59mp-jv5r (server-action DoS) affects the app. Upgrade to 15.5.28.
  - GHSA-2464-fhr4-w9xw (critical, image-optimizer RCE): the advisory's workaround is sharp ≥0.35.5, and the lockfile pins 0.35.5, so `npm ci` on Render is covered. The app also uses no SVG and no `next/image`. Upgrade anyway.
- `@paypal/agent-toolkit@1.11.0` pulls in `@langchain/core`, `ai`, `mathjs`, `jsondiffpatch`, `langsmith`, `uuid` and `undici@7.30.0` (all flagged). They load only in live AI mode, and I could not find attacker input reaching them. Since only four read endpoints are used, I'd replace the toolkit with direct REST calls.
- `zod@3` (memory exhaustion on oversized constrained collections): no attacker-shaped validation path, Low.
- `postcss` and `vite` advisories are build/dev only.

**F15 Memo side channel (Low, live)**
- **What's wrong:** A prompt-injected agent can choose `sourceRef` (format-validated), and its first 19 characters go into the PayPal note and Stellar memo the recipient sees. The agent can read vendor bank labels (`lookup_vendor`) and PayPal transaction history.
- **Fix:** Use the evidence-bound reference for the memo, or the obligation id only.

**F16 Storage (Low)**
- **What's wrong:** Every upload (up to 10 MB) is stored as a BLOB, even when it is never attached, and nothing ever deletes it.
- **Fix:** Add a quota and purge unlinked uploads after N hours.

**F17 Amend payee change (Low)**
- **What's wrong:** The validator accepts `vendorId` and `currency`, so a direct action call can change the payee of a pre-approval obligation. Warnings appear and one approval clears them.
- **Fix:** Drop `vendorId` from amend, or require a fresh approval from a second person.

**F18 Tick CSRF (Info)**
- **What's wrong:** A cross-origin form POST runs an autopilot pass. It can only do what policy already allows.
- **Fix:** Check Origin, or require a bearer token for the scheduler.

### 4. Non-security bugs
- `readDocument` receives the raw MIME type, not the normalised one (attachments.ts:27 vs :302). `text/plain; charset=utf-8` or `application/PDF` is accepted at upload but then read as "unsupported".
- `matchVendor` builds `new RegExp("\\b"+part+"\\b")` from vendor names without escaping (extractor.ts:74). A name containing `(`, `+`, `*` or `?` throws and breaks ingest. It is latent today, since vendors are seed-only.
- Dual approval can never be satisfied, and live-mode separation of duties deadlocks with one credential (F5).
- `findByIdempotencyKey` calls `GET /v1/payments/payouts?sender_batch_id=`. I could not confirm that query exists in the Payouts API. If it doesn't, the lookup always returns null. That is safe (the outcome stays unknown) but means reconcile never finds anything that way.
- PayPal `getStatus` treats a batch-level SUCCESS as item success when `items` is missing.
- Maria and Rosa share `DEMO_PAYPAL_RECIPIENT` in live mode, and nothing flags two vendors with the same payout destination.
- `approveAction` trusts client-sent `shownFingerprints`. That is fine as a UI check, but it is not a control.

### 5. What is done well
- **Middleware and actor:** The middleware overwrites `x-checkrail-user`, and actions trust it only when auth is on. Spoofing failed and the audit showed `user:judge`.
- **Server actions:** Origin is checked (an evil Origin returned a 500 digest). Actions are not executed on 404 or excluded paths.
- **Image optimizer:** It cannot fetch attachments, because its internal fetch passes through the middleware.
- **Execution:**
  - immediate transaction, CAS transitions, refusal while any attempt is open;
  - same-key replay;
  - "unknown" never collapses to "failed";
  - Stellar loads the account before the history search, then serialises submissions;
  - payout hash re-checked inside the lock;
  - response redaction.
- **Webhook:** It only triggers a poll and returns 404 in mock.
- **Policy and agent:** Policy is deterministic and the AI can only add warnings. Model output is clamped and the PayPal tools are filtered to read-only.
- **Inputs and rendering:**
  - Drizzle everywhere, with no raw SQL injection surface;
  - no `dangerouslySetInnerHTML`;
  - attachments served with nosniff, a sandbox CSP and sanitised filenames, behind a MIME allowlist;
  - CSV formula prefixing, apart from the CR gap in F7.

### 6. Ratings
- **Overall security: 6/10.** The core payment engine is better than most hackathon code and held against my race, idempotency and state-machine probes. But the controls the product advertises (dual approval, separation of duties, autopilot caps, independent evidence) are weak or easy to switch off. That comes from the single shared identity, the "0 = unlimited" caps and invoices that count as their own proof. On top of that, one crafted document takes the server down, and the deployment defaults fail open and wipe data on boot.
- **Fit to run the hosted hackathon demo: 7/10.** Mock rails mean no money is at risk and Basic auth keeps strangers out. The main exposure is a judge (or anyone with the published credential) freezing or resetting the shared instance. Upgrading Next and capping the extractors and PDF parsing would take it to 8 or 9.
- **Fit to move real money for a small business today: 3/10.** It needs per-user identity and roles, hard autopilot caps, evidence independent of the payee, a seed that cannot wipe live data, enforced auth, DoS hardening and an audit-volume fix first.
