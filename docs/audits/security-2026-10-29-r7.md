## 4. The duplicate rule: trying to pay one job twice

The rule (`policy.ts`, "committed", "earlier"): money that is committed (approved, in flight, paid, disputed) always counts as already used; an open request counts only if it was created earlier; blocked, cancelled, failed and refunded never count; drafted and needs-evidence never count as originals. `orchestrator.ts` passes `createdAt`, and a missing time counts as earlier (conservative); equal times are separated by id.

Scenarios run over HTTP, all with operator evidence so I controlled approval and payment:

- **D1, resend while the original is open.** A filed, B (same reference) filed: B blocked "already used by A (awaiting_approval)". A rejected, B rechecked: B passes, approved, paid. A third copy C: blocked "already used by B (settled)". One settlement.
- **D2, the original needs evidence.** A filed with no evidence (needs_evidence); B filed with evidence passes and is paid. The vendor then uploads the evidence for A through its evidence link: A is blocked "already used by B (settled)". One settlement.
- **D3, two copies at once, approved and paid at once.** The second copy was blocked at filing; an approve-and-pay by both left one settled, one blocked. One settlement.
- **D4, a blocked original and a resend.** A blocked (amount mismatch), B paid, then A amended to the right amount: A is blocked "already used by B (settled)". One settlement.

Reasoning for what I could not force. If two copies were filed so that both were evaluated before either moved out of drafted, both would sit in awaiting_approval. Approving the later one runs policy again, sees the earlier one open, and blocks it; approving the earlier one commits it, and the later is then blocked at its own approval or at execution. If both ever became approved, each would count the other as committed and `executeObligation`'s policy re-run would refuse both: a stuck pair (availability), not a double payment, and a person unblocks one. The `OPEN_ATTEMPT` guard and the compare-and-swap still cover one obligation executed twice (eight parallel calls in round 5 produced one attempt).

The only ways the rule lets the same job through are the intended ones: the earlier payment was refunded (SEC3-1 trust, section 5), failed, or marked failed by a person's "nothing moved" claim (SEC7-1). I found none other.

## 5. PR6-9: payout and reversal tied in one pass

Code: `books.ts` `trusted = source === "paypal_api" || canRecord` and `passPayoutDate`; a date check on every anchor.

Attacks (a reconciler is the accountant; a "tampered" file is one I wrote by hand):

| Case | Result |
|---|---|
| Clerk uploads one file with payout and reversal | Listed "the payout it reverses is only in this same file"; nothing applied; payment stays settled |
| Accountant uploads one hand-edited file with payout and reversal | **Refunded** (this is the relaxation) |
| Reversal from a different sender address | Refused: "amount, currency or sender does not match" |
| Wrong amount, wrong currency | Refused |
| Reversal dated three days before the payout, same file | Refused: "dated before the payout it reverses" |
| Reversal of vendor X citing vendor Y's payout id | Refused |
| Two reversals of one payout | First applied, second refused |
| Payout tied in an earlier upload, reversal dated two days before | Refused |
| Clerk plants a payout (saves nothing), accountant uploads only the reversal | Refused: "not matched to a payment here" |
| Reversal with an unparseable date ("yesterday") | **Applied.** `books.ts` skips the check when either date is not `YYYY-MM-DD`. |

Do I accept the relaxation? **Yes, with conditions.** The rule asked for in round 2 defended against a file that carries both halves. What it never defended against is a reconciler uploading a file whose lines are false, and in round 6 I showed that the old two-upload rule already refunds a payment when the accountant uploads two clerk-supplied files. A reconciler can also refund any settled payment by hand with `markReturnedByHand`, which takes a transaction id they name. So the change gives a reconciler no new power and a clerk none; it removes one step of friction. The checks that carry weight (sender, amount, currency, and now the date) hold in every case above except the unparseable date, which gives a tampered file nothing it could not get with a valid date (Info, SEC7-4: fail closed on an unreadable date). My conditions, for real money: refunds applied from an uploaded CSV should either come only from the PayPal API source or be listed for a second person's confirmation, and the accountant's training should say that the statement must come from PayPal, not from the clerk.

## 6. SEC5-4 on PayPal: reproduction

Script `r7-work/sec54.ts`, network stubbed. The stub accepted the PayPal sandbox host only, answered the token call, recorded each payout POST, and in "outage" mode threw on every other call.

1. `executeObligation` with the real `PayPalRail`: the POST reached the stub (batch `dad7c1d5...`, USD 180.00 to the vendor) but the answer was lost. Result: `unknown`, state `execution_pending`.
2. `pp.findByIdempotencyKey(...)` during the outage: `null`.
3. `resolveManually(..., {kind:"nothing_moved"})` during the outage: returned `failed` (accepted).
4. `retryFailed`, network back, `executeObligation`: `submitted`. The stub now holds two payouts with different `sender_batch_id` (`dad7c1d5...` and `c6c17224...`) for one obligation.

Cause: `paypal.ts:174-181` swallows token and transport failures and any non-2xx (a 404 for "no such batch" is indistinguishable from a 503), returning `null`; `orchestrator.ts` (the block added before the `nothing_moved` update) treats `null` as "provider knows nothing". The new unit test uses a scripted rail that throws, so it does not exercise the real adapter. Fix: in `PayPalRail.findByIdempotencyKey`, throw on token failure, `transportError`, 5xx, 408 and 429; return `null` only for a definitive not-found. Add a test with the real adapter and a stubbed `fetch`. Label: Medium, Should-fix, first item before the first real payment.

## 7. Other new code

### The Approve button on the run page (`runs.ts`, `RunActions.tsx`)

- Server side, `approveAction` still does `actOn(id, "approve")`, `approvalGate` (limit, covering approver, separation of duties) and the fresh-policy comparison against the list sent.
- Tested: the clerk and the accountant get no button and the action refuses them; the capped approver is refused on a USD 2,000 item; the owner is refused on a request the owner prepared, also as persona Minh; an empty or invented fingerprint list is refused ("Something changed since this page was checked"); the full UI call succeeds only for the right person.
- `viewRun` is read-only (section 3).
- Caveat (**SEC7-2, Low**): the list is optional on the server action. A call that omits it falls back to "the last evaluation on record" and succeeds for an approver. Both UI callers (`DecisionCard`, `ActionBar`, `RunActions`) send the list, so the claim "the approval covers exactly what the person saw" holds for the UI, not for a hand-made call. The person making it already holds the approve right and limit. Make the action require the list; keep the fallback in the engine for scripts.
- Cosmetic: the run confirmation text reads "1 carryes a warning" (typo).

### Manifest re-check (`manifest.ts`, `rates.ts`)

- Only `verify_vendor` can import (clerk and accountant refused, again). The re-check can only run `recheckVendorItems` on waiting requests for the vendors touched. It never records a human approval and never pays.
- It can, however, **clear a waiting request to `approved`**: a clerk's request with a document-provenance PDF for a departure not yet on file waited as `awaiting_approval`; after an approver imported the departure it became `approved` / `auto_execute` with 0 approvals and no payment attempt. The import message said only "4 waiting payments were checked again". That is the SEC6-2 residual by another route, not new power, but the approver is not told that requests were released (**SEC7-5, Low**). Say how many are now cleared to pay, list them, or leave them for a person.

### Stated-unit-rate warning (`statedRate.ts`)

- **ReDoS: no.** Thirteen inputs of about 20,000 characters (digit and space runs, repeated "4 days at", comma groups, price tokens, ambiguity between `per` and `a`, a long leading space run) each ran in under 3 ms. The patterns are bounded and the text is split on newlines first.
- **Suppression: yes, trivially, and it is a heuristic.** A vendor avoids it with "four days", "= USD 4000", "in total", a zero-width character inside the number, or a total only. It only ever adds a warning, so evasion cannot loosen anything that was blocked or required approval; the existing rate-card block still applies when a departure is on file.
- **A false warning:** a trip sheet line that names two vendors can raise it, and a literal `\u0001USD:100\u0001` in the text replaces the next price. Neither is a risk beyond an extra warning.

### Aged payables and exports (`accounting/*`, `bills.ts`)

- The settlement CSV and the Xero bills file use `csvCell` on every cell; description and reference come from validated ASCII references and the vendor role. A formula in the vendor's account code is refused at input (20 characters, restricted), so no formula reaches a file. Aged payables is not exported; the "reference" fallback (first words of the raw request) is rendered by React. No injection or leak found.

### Remittance, onboarding and evidence pages

- `PublicFrame` writes `document.documentElement.lang=` plus `JSON.stringify(tag)` where `tag` must match `/^[a-z]{2,3}$/`. A `?lang=en"><script>alert(1)</script>` query fell back to `en`; the payload appears only inside the framework payload as `<...`, not as markup. This is the only `dangerouslySetInnerHTML` in the source.
- Tokens: 192-bit, hashed at rest, unknown tokens answer 200 with a generic "not valid" page of the same shape, public paths are throttled 30 a minute per key. The remittance page shows business, vendor, amount, rail, date and the provider's reference; no internal id, e-mail or account number (checked). Remittance links stay valid 90 days and can be opened repeatedly (accepted in round 5).
- `onboarding-strings.ts` turns engine errors into a code; unknown ones become a generic sentence in the vendor's language. The action still returns the English engine message beside the code (`onboard/actions.ts`), which can include text from an unexpected exception; return only the code to an unauthenticated caller (Info).

### Static 401 page and middleware

- The 401 body is a constant (1,222 bytes); a path and a header full of markup were not reflected; security headers and the CSP are present on it.
- `CHECKRAIL_LOG_CLIENT_IP=1` logs the throttle key and four address headers, never the password. Off by default.
- **`CHECKRAIL_THROTTLE_SPARES_VALID=1`.** With it set, 14 wrong guesses gave 11 × 401 then 429 × 3; a correct password then got 200, and so did the correct password of a *second, secret* account on the same instance. Wrong guesses after the limit return 429 immediately and are not counted. So the flag removes the throttle for every configured account, not just the published judge login. Off (the default), the correct password is refused after the limit exactly as before (verified). `render.yaml` sets it to 1, which is right only if `CHECKRAIL_USERS` on that service holds nothing but published logins. **SEC7-3, Low:** make the flag a no-op when real money can move (`realMoneyEnv`) or when more than one account is configured, and say so in the log at start-up.
- Where the login is secret and the flag is off, the throttle is unchanged from round 5: it is only as good as the address header (`throttle.ts` is not in this diff).

## 8. Contract (source and tests)

`cargo test --locked`: 20 passed. I re-read the full diff and ran my random walk.

- **Expiry.** `expires_at = release_at + PROPOSAL_LIFE` (3 days). `release` refuses `now > expires_at`; `expire` refuses `now <= expires_at`; at exactly `expires_at` only release works, so the two never overlap and never both fail. A released, cancelled or expired payment cannot be swept again (`NotPending`). Anyone can sweep; sweeping subtracts the amount from the pending total and moves nothing. The owner can still cancel an expired but unswept proposal.
- **Cap accounting after sweeping.** The pending total is reduced exactly once per proposal. My random walk (6,000 steps, 70 releases, 13 expiries, 30 cancels, payee toggles, cap changes, time jumps up to 4 days) checked after every step that `scheduled_total` equals the sum of what is still pending, that the amount released in any true 24-hour window never exceeds the cap in force at that release, and that the spend list never exceeds 25 entries (longest seen: 15). No violation. (An earlier run, dominated by expiries, also passed.)
- **Time-to-live.** `keep_alive` tops up the instance entry on every call; payments and payees are topped up where a call touches them; `extend_ttl` is only called on entries that exist (after a `set`, or after `is_allowed` is true). Threshold 30 days, extend to 60, well under the network maximum. An allow-listed payee nobody uses for 60 days can still be archived; the next `propose` then fails until someone restores it (liveness only). A failed call reverts its own extension, which is harmless.
- **Remaining:** an expired proposal keeps counting against the daily cap until someone calls `expire`, and the app has no keeper for that (the contract is not wired). Document it. Changing `Payment` changes the stored layout, which is fine for a contract that has not been deployed.

## 10. The earlier decisions, revisited

1. **Assist-mode clerks sending cleared payments: accept, now in full.** Round 6's condition (no rate-card support before the departure ends) is in and works. 4. **npm audit acceptance: accept** (section 9).

## 12. Ratings

- **Overall security: 8/10 (round 6: 8).** The authorization perimeter, dual control, the duplicate rule, the refund checks, the contract and the new pages survived hostile testing, and the diff adds no Critical or High; it stays at 8 because one headline fix (SEC5-4 on PayPal) does not do what the response says, and the system has still never had a human audit.
